# Лабораторная работа 2. Потоки, процессы, асинхронность

## Цель работы

Цель работы - сравнить три способа конкурентного выполнения задач в Python: `threading`, `multiprocessing` и `asyncio`. В работе реализованы две задачи: вычисление суммы большого диапазона чисел и параллельный парсинг HTML-страниц с сохранением результата в PostgreSQL через модель лабораторной работы 1.

## Задачи

1. Вычислить сумму целых чисел от `1` до `10_000_000_000_000` включительно тремя способами: потоками, процессами и asyncio.
2. Скачать HTML-страницы из общего списка URL, извлечь тег `<title>` и сохранить результат как объект `Hackathon` в PostgreSQL-базу из лабораторной работы 1.

## Реализация задачи 1

Диапазон `1..limit` разбивается функцией `split_into_chunks` на непересекающиеся части. Для каждой части вычисляется сумма по формуле:

```python
count = end - start + 1
partial_sum = count * (start + end) // 2
```

Контрольное значение:

```python
expected = limit * (limit + 1) // 2
```

Для `10_000_000_000_000` ожидаемая сумма равна `50_000_000_000_005_000_000_000_000`.

В режиме `--iterative` используется прямой перебор `sum(range(start, end + 1))`. Этот режим предназначен только для уменьшенных диапазонов, потому что перебор до `10^13` практически невыполним.

## Реализация задачи 2

Общий список URL находится в `lab_2/task_2/urls.py`. Синхронные реализации используют `requests`, асинхронная - `aiohttp`. HTML разбирается через `BeautifulSoup`, функция `extract_title` удаляет лишние пробелы из заголовка.

Результат сохраняется в существующую модель из лабораторной работы 1:

```python
Hackathon(
    title=page_title,
    description=f"Imported from {url}",
    city="Online",
    format=HackathonFormat.online,
    duration_hours=1,
    organizer_id=None,
)
```

Для каждого URL создаётся отдельная `Session`. Нельзя делить один объект `SQLModel Session` между потоками, процессами или асинхронными задачами, потому что сессия хранит внутреннее состояние транзакции, identity map и соединение. Совместное использование может привести к гонкам, повреждению состояния и ошибкам соединения.

## Threading

`threading` создаёт несколько потоков внутри одного процесса. Потоки удобны для I/O-bound задач: пока один поток ждёт сеть или базу данных, другой может продолжать работу. В CPU-bound Python-коде ускорение ограничено GIL.

## Multiprocessing

`multiprocessing` запускает отдельные процессы. У каждого процесса свой интерпретатор Python и свой GIL, поэтому подход позволяет задействовать несколько ядер CPU. Минусы - более высокие накладные расходы на создание процессов, сериализацию аргументов и передачу результатов.

## Asyncio

`asyncio` использует один поток и цикл событий. Подход эффективен, когда много операций ожидания: сетевые запросы, таймеры, ожидание БД. `asyncio` сам по себе не превращает CPU-bound код в параллельный, поэтому для короткой формульной суммы ускорение не ожидается.

## GIL

GIL - глобальная блокировка интерпретатора CPython. Она не позволяет нескольким потокам одновременно выполнять Python bytecode в одном процессе. Поэтому потоки хорошо подходят для ожидания I/O, но не дают полноценного параллелизма для CPU-bound вычислений на чистом Python.

## Конкурентность и параллелизм

Конкурентность означает, что программа ведёт несколько задач в один период времени и переключается между ними. Параллелизм означает реальное одновременное выполнение на нескольких ядрах. `asyncio` и `threading` часто дают конкурентность, а `multiprocessing` может дать настоящий параллелизм.

## CPU-bound и I/O-bound

CPU-bound задачи ограничены скоростью процессора. Пример - прямой перебор большого диапазона чисел. I/O-bound задачи ограничены ожиданием внешних ресурсов: сети, диска, базы данных. Парсинг страниц в этой работе относится в основном к I/O-bound задачам.

## Разбиение URL

Все три парсера используют один список URL, одинаковый timeout и одинаковое количество работников. В `threading` URL распределяются между потоками через `ThreadPoolExecutor`, в `multiprocessing` - через `ProcessPoolExecutor`, в `asyncio` ограничение одновременных запросов задаётся через `asyncio.Semaphore`.

## Анализ времени

Для аналитической формулы вычисление слишком короткое, поэтому время в задаче 1 в основном отражает накладные расходы на создание потоков, процессов и задач asyncio. На малых объёмах multiprocessing может быть медленнее из-за запуска процессов, но в настоящих CPU-bound задачах он способен использовать несколько ядер.

В задаче 2 результаты зависят от сети, удалённых серверов и состояния PostgreSQL. В текущем запуске `httpbin.org/html` вернул `503 Service Temporarily Unavailable`, а один асинхронный запрос к `fastapi.tiangolo.com` получил ошибку DNS. Эти ошибки зафиксированы как `failed`, остальные URL продолжили обработку. Самый быстрый результат одного запуска нельзя объявлять универсальным правилом.

## Ограничения эксперимента

Время сетевого парсинга нестабильно из-за внешних сайтов и качества соединения. Запись в PostgreSQL зависит от локальной базы и применённых миграций. Итеративный режим задачи 1 нельзя запускать с лимитом `10^13`.

## Вывод

Потоки полезны для I/O-bound задач, процессы - для CPU-bound задач с реальным параллелизмом, а asyncio эффективно управляет большим количеством операций ожидания. Для корректного сравнения важно использовать одинаковые входные данные и фиксировать реальные замеры, а не заранее заданные числа.
